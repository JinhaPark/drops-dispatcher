# [How Good Is AI at Coding React (Really)?](https://addyo.substack.com/p/how-good-is-ai-at-coding-react-really)

2025.12.29 · Addy Osmani · Elevate

AI가 React 코드를 얼마나 잘 만드는지는 과제의 범위에 따라 크게 달라집니다. Addy Osmani는 독립적인 컴포넌트나 명확한 요구를 구현하는 작업과, 여러 파일과 상태가 얽힌 기능을 통합하는 작업을 구분합니다. 후자로 갈수록 실패가 늘어나는 현상을 여러 벤치마크와 개발 경험으로 설명합니다. 실행되는 코드와 사용하기 좋은 화면도 서로 다른 평가 대상입니다. 저자는 논리 구현 능력만으로 시각적 위계, 일관된 디자인, 접근성과 유지보수 품질까지 보장할 수 없다고 강조합니다.

결과를 개선하는 방법은 모델 선택에만 있지 않습니다. 컴포넌트의 입력값, 상태, 변형, 키보드 동작과 오류 표시를 먼저 정하고, 팀의 디자인 규칙을 명시합니다. 생성한 코드는 기존 훅과 상태 관리, 스타일 체계에 맞춰 통합합니다. 작업을 작은 단계로 나누고 변경 범위를 제한하며, 실패한 테스트와 화면 정보를 다시 제공하는 방식입니다. 많은 자료를 무작정 넣는 대신 현재 과제를 해결하는 데 필요한 맥락을 고르는 일이 중요하다는 주장입니다.

글은 도구의 역할도 구분합니다. Context7은 버전에 맞는 문서를 공급하고, Next.js DevTools MCP는 실행 중인 앱의 오류와 구조를 전달하며, Chrome DevTools MCP는 실제 브라우저에서 동작을 확인하도록 돕습니다. 생성형 제작 도구의 결과는 아이디어를 얻는 데 활용하되, 제품에 넣기 전에 코드 구조와 디자인 체계를 정리하라고 권합니다. 이들은 저자가 소개한 당시의 작업 방식이며, 벤치마크 순위가 개별 팀의 성공률을 그대로 예측한다는 뜻은 아닙니다.

편집자의 해석으로는 화면이 그럴듯한지 확인하는 단계와 사용자 행동이 맞는지 확인하는 단계를 따로 설계할 필요가 있습니다. 가입 버튼 하나도 요청을 보내는 동안의 중복 클릭, 실패 후 재시도, 키보드로 이동한 초점까지 살펴야 합니다. 이런 조건을 합의하면 외형이 비슷한 두 구현 중 어떤 것을 채택할지 설명하기 쉬워집니다. 예시는 원문의 실험 결과가 아니라 적용을 위한 판단 기준입니다. 또한 브라우저 도구로 확인한 한 화면이 모든 기기와 사용자 상황을 대표하지는 않습니다. 기존 컴포넌트와 실제 사용자 흐름을 기준으로 검증 범위를 정해야 합니다. AI가 생성한 초안의 양보다 팀이 이해하고 계속 수정할 수 있는 결과를 남기는지가 실질적인 성과 기준입니다.
