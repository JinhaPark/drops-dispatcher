# [The Prompt Engineering Playbook for Programmers](https://addyo.substack.com/p/the-prompt-engineering-playbook-for)

2025.05.27 · Addy Osmani · Elevate

AI에게 코드를 부탁할 때 결과를 좌우하는 요소는 무엇을 만들고 어떤 조건을 지켜야 하는지 전달하는 능력입니다. Addy Osmani는 프롬프트 작성을 동료에게 문제를 설명하는 과정으로 풀어냅니다. 모델은 프로젝트의 의도와 환경을 저절로 알지 못하므로 언어, 사용 기술, 관련 코드와 기대 결과를 함께 제공해야 합니다. 글은 디버깅, 리팩터링, 새 기능 구현을 중심으로 이러한 원칙을 구체화합니다.

디버깅에서는 실제 오류와 기대 동작의 차이를 명확하게 제시하고, 가능하면 문제를 재현하는 작은 코드로 범위를 좁힙니다. 코드 구조를 바꾸는 리팩터링에서는 가독성, 속도, 중복 제거 중 무엇을 개선할지 정해야 합니다. 기존 오류 처리처럼 유지해야 할 동작도 조건에 포함합니다. 새 기능은 계획을 먼저 세우고 작은 단계로 구현하며, 기존 코드의 관례와 입출력 예시를 전달하는 방식입니다.

저자는 첫 답을 그대로 받아들이기보다 설명을 요구하고 결과를 시험하면서 요청을 수정하자고 권합니다. 모호한 목표, 한꺼번에 몰아넣은 작업, 불분명한 코드 지칭은 흔한 실패 원인입니다. 검토자나 멘토라는 역할을 지정하는 방법도 소개하지만, 역할 설정이 정확성을 보장하지는 않습니다. 글의 여러 응답 비교는 설명을 위한 가상 예시이므로 도구 성능의 실험 결과로 읽어서는 안 됩니다. 최종 판단에는 실제 실행과 검토가 필요합니다.

실무에서는 프롬프트를 작성하는 시간을 요구사항을 발견하는 시간으로 활용할 수 있습니다. 예를 들어 출석 명단을 정리하는 프로그램을 만든다고 가정합니다. 같은 이름을 한 사람으로 합칠지, 학번이 비어 있으면 어떻게 표시할지 먼저 적어 보면 자연어 요청에 숨어 있던 결정이 드러납니다. 이는 원문에 없는 적용 예시입니다. 이런 결정을 사람이 정한 뒤 서로 다른 입력 자료로 결과를 확인하면, 답이 마음에 들지 않을 때도 무엇이 잘못됐는지 구체적으로 설명할 수 있습니다. 한 번의 멋진 질문을 찾기보다 합의한 조건과 관찰한 결과를 남기는 편이 다음 수정과 동료 검토에도 유리합니다. 조건이 바뀔 때의 영향도 함께 기록합니다. 프롬프트는 그 과정에서 작은 작업 명세의 역할을 맡게 됩니다.
