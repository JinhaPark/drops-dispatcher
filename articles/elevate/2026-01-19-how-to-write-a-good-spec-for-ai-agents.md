# [How to write a good spec for AI agents](https://addyo.substack.com/p/how-to-write-a-good-spec-for-ai-agents)

2026.01.19 · Addy Osmani · Elevate

AI 에이전트에게 긴 명세를 한꺼번에 전달한다고 요구사항을 더 잘 지키는 것은 아닙니다. Addy Osmani는 목적이 분명하고 필요한 정보를 찾기 쉬우며 작업에 따라 갱신되는 명세를 제안합니다. 사용자와 해결할 문제, 성공 조건을 먼저 정한 뒤 AI가 세부 계획을 작성하게 하고 사람이 검토합니다. 읽기 전용 계획 단계에서 모호한 점을 해결하고, 승인한 내용을 파일로 남겨 다음 작업에서도 참조하도록 하는 방식입니다.

명세에는 실행 명령, 테스트 방법, 프로젝트 구조, 코드 스타일, Git 작업 방식, 변경 권한의 경계를 담습니다. 추상적인 설명보다 실제 명령과 코드 예시가 도움이 된다는 설명입니다. 요구 정의, 기술 계획, 작은 작업 분해, 구현을 구분하고 각 단계에서 결과를 확인합니다. 문서가 커지면 요약 목차와 세부 항목을 연결해 필요한 부분만 제공합니다. 여러 에이전트를 사용하더라도 서로 수정할 파일과 공유해야 할 계약을 분명히 해야 한다고 강조합니다.

행동 경계는 항상 수행할 일, 먼저 확인할 일, 금지할 일로 나눕니다. 구현 뒤에는 명세와 결과를 비교하고, 입력과 예상 출력을 정한 검증 사례로 동작을 확인합니다. 사람이 가진 업무 지식과 예외 조건도 명세에 반영합니다. 요구가 바뀌면 문서와 계획, 코드를 함께 수정하고 이력을 남깁니다. 저자는 간단한 작업에 과도한 문서가 필요하지는 않다고 덧붙이며, 명세의 상세함을 문제의 복잡도에 맞추라고 권합니다. 명세는 실행 중에도 유지하는 작업 기준입니다.

편집자의 해석으로는 명세의 품질을 길이보다 판단 가능한 문장의 비율로 살필 수 있습니다. 예를 들어 검색이 빨라야 한다는 요구에는 어떤 데이터와 조건에서 무엇을 측정할지 빠져 있습니다. 이를 채우는 과정에서 성능뿐 아니라 정확성이나 운영 비용과의 선택도 드러납니다. 이 예시는 원문이 검증한 작성 공식이 아니라 검토를 돕는 방식입니다. 또 문서에 금지 사항을 적는 것과 도구의 권한을 실제로 제한하는 것은 별개의 일입니다. 중요한 경계에는 실행 환경의 통제가 필요합니다. 팀은 에이전트가 성공했다고 보고할 때 확인할 자료와 미완료 조건을 함께 정의할 수 있습니다. 그러면 명세는 일방적인 지시 목록을 넘어 사람이 결과를 채택할 근거를 정리하는 문서가 됩니다.
