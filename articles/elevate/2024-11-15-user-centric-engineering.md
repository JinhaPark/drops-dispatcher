# [User-centric engineering.](https://addyo.substack.com/p/user-centric-engineering)

2024.11.15 · Addy Osmani · Elevate

기술적으로 정교한 시스템도 사용자가 문제를 해결하지 못하면 좋은 제품이라고 하기 어렵습니다. Addy Osmani는 사용자의 경험을 공학적 의사결정의 기준에 포함하자고 주장합니다. 개발 전에는 대상 사용자와 실제 문제를 확인하고, 개발 중에는 처음 사용하는 사람이 어디서 멈추는지 살핍니다. 출시 뒤에도 지원 요청과 사용 양상을 통해 가정을 점검합니다. 사용자가 요청한 기능을 그대로 구현하는 것만으로는 충분하지 않습니다. 요청 뒤에 있는 목적을 이해해야 더 간단하고 효과적인 해결책을 찾을 수 있습니다.

사용자 관점은 화면 구성뿐 아니라 시스템 설계에도 영향을 줍니다. 저자는 체감 속도, 복구 가능한 오류, 일부 기능에 문제가 생겨도 나머지는 유지되는 동작, 기존 작업 흐름과의 호환성을 예로 듭니다. 인터페이스에서는 이해하기 쉬운 표현과 합리적인 기본값이 중요합니다. 이를 위해 직접 사용자와 만나고 지원 담당자나 조사 담당자와 협력하며 사용 데이터를 함께 분석하자고 제안합니다. 공감은 기술적 정확성을 대신하는 감상이 아니라 어떤 문제를 먼저 해결할지 판단하는 정보입니다. 장기적인 유지 가능성과 당장의 요구를 조정하는 책임도 남습니다.

실무에 옮긴다면 기술 개선안에 사용자가 겪는 구체적인 장면을 붙이는 방법이 유용합니다. 예를 들어 평균 처리 시간이 짧아졌다는 설명만으로는 작업 도중 멈춘 사용자의 어려움을 파악하기 어렵습니다. 입력한 내용을 잃는지, 다시 시도할 수 있는지, 다음 행동을 이해하는지까지 확인하면 개선의 목표가 달라집니다. 같은 오류라도 사용자의 업무와 발생 시점에 따라 손실이 다를 수 있으므로 단순한 발생 횟수와 실제 영향을 구별해야 합니다. 이러한 질문은 설계 검토를 더 구체적으로 만듭니다.

사용자 중심이라는 표현이 모든 요청을 수용하라는 명령이 되어서는 안 됩니다. 제한된 예산과 일정 아래에서는 여러 사용자 집단의 요구가 충돌할 수 있습니다. 이때 필요한 것은 가장 목소리가 큰 사람의 요구를 따르는 태도보다 선택의 근거를 설명하는 절차입니다. 어떤 불편을 먼저 줄이고 어떤 제약을 남기는지 기록하면 이후 피드백과 비교할 수 있습니다. 담당 역할을 모두 합칠 필요도 없습니다. 개발자와 기획자, 디자이너가 같은 사용 상황을 이해하면서 각자의 전문성을 보태는 협업이 이 글의 관점을 실행하는 현실적인 방법입니다.
