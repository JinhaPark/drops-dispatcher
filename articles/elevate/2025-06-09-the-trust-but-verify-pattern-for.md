# [The "Trust, But Verify" Pattern For AI-Assisted Engineering](https://addyo.substack.com/p/the-trust-but-verify-pattern-for)

2025.06.09 · Addy Osmani · Elevate

AI가 코드를 빠르게 생성해도 전체 개발 과정이 같은 비율로 빨라지지는 않습니다. Addy Osmani는 사람이 그 코드를 이해하고 확인하는 일이 새로운 병목이 될 수 있다고 설명합니다. 실행되는 코드에도 잘못된 업무 규칙, 취약한 예외 처리, 오래된 사용 방식이 숨어 있을 수 있기 때문입니다. 글의 핵심은 AI의 도움을 받아 초안을 만들되, 완료 여부는 별도의 검증으로 판단해야 한다는 원칙입니다.

검증은 여러 층으로 구성합니다. 동료 검토에서는 요구사항과 설계의 적합성을 확인하고, 자동화된 테스트에서는 개별 기능과 다른 구성요소의 연결을 시험합니다. 정적 분석과 의존성 점검도 보완 수단입니다. 저자는 특히 AI가 만든 테스트가 구현의 잘못된 가정을 그대로 반복할 수 있다고 지적합니다. 테스트가 통과했다는 표시만 볼 것이 아니라 어떤 동작을 실제로 확인하는지 읽어야 합니다. 존재하지 않는 라이브러리 제안도 확인 대상으로 다룹니다.

검토 부담을 줄이려면 결과물을 작은 단위로 나누고, 처음부터 제약과 검증 기준을 알려 주는 편이 유리합니다. 저자는 다른 모델의 평가나 수학적으로 성질을 확인하는 기법도 가능성으로 소개합니다. 다만 이런 방법이 복잡한 소프트웨어의 정확성을 모두 보장한다는 뜻은 아닙니다. 팀은 생성에 걸린 시간뿐 아니라 검토와 수정에 필요한 시간을 함께 계획해야 합니다. 최종 결과에 대한 책임은 사람에게 남는다는 설명입니다.

이를 작업 계획에 적용하는 편집상의 예시는 공용 파일 정리 기능입니다. AI가 오래된 파일을 찾는 코드를 금방 작성했더라도, 실제 삭제 전에 어떤 파일이 대상인지 목록을 만들고 담당자가 확인하는 단계를 별도로 둡니다. 같은 이름의 파일, 잘못된 날짜 정보, 실행 중 새로 생성된 파일처럼 상황을 바꾸어 보면 기능의 기준이 분명해집니다. 이 사례는 원문 내용을 구체화하기 위해 새로 구성한 것입니다. 생산성을 계산할 때는 코드 작성 시간과 확인 시간, 오류를 복구하는 시간을 함께 비교할 수 있습니다. 이런 비교를 해 보면 어떤 작업은 자동화의 이익이 크고, 어떤 작업은 먼저 명세를 단순하게 만드는 일이 더 효과적인지 판단할 수 있습니다.
