# [Vibe Coding is not an excuse for low-quality work](https://addyo.substack.com/p/vibe-coding-is-not-an-excuse-for)

2025.04.18 · Addy Osmani · Elevate

자연어로 원하는 기능을 설명하고 AI가 코드를 작성하게 하는 바이브 코딩은 개발의 진입 장벽을 낮춥니다. 그러나 Addy Osmani는 화면이 작동한다는 사실만으로 제품의 품질을 판단해서는 안 된다고 강조합니다. 빠르게 만든 코드에 예외 처리, 보안 점검, 설계의 일관성이 빠져 있으면 나중에 수정하는 비용이 커지기 때문입니다. 생성 속도가 올라갈수록 사람이 이해하지 못하는 코드도 빠르게 쌓일 수 있다는 문제의식입니다.

저자는 AI의 결과물을 검토가 필요한 초안으로 다루자고 제안합니다. 개발자는 코드를 읽고 동작을 설명하며, 복잡한 구현을 작은 부분으로 나누고 입력 조건과 인터페이스를 분명히 해야 합니다. AI가 작성한 테스트도 같은 잘못된 가정을 반복할 수 있으므로 검증 대상으로 삼습니다. 팀의 설계 기준에 맞는지 살피고, 예상하지 못한 입력과 실패 상황을 시험하는 과정까지 포함해야 작업을 마쳤다고 판단할 수 있습니다.

활용 범위에 따라서도 접근이 달라집니다. 저자는 시제품, 일회성 도구, 반복적인 기본 코드처럼 목표가 명확한 작업에서 장점을 찾습니다. 반면 복잡한 업무 규칙이나 긴 유지보수 기간이 중요한 시스템에서는 초기 속도만 보고 판단하기 어렵다고 설명합니다. 설계 결정의 이유를 남기고 동료가 검토할 수 있게 해야 합니다. AI가 계속 이해하기 어려운 해법을 내놓는다면 직접 구현으로 돌아가는 선택도 필요합니다.

이를 실무에 적용하면, 시제품이 정식 서비스로 바뀌는 시점을 별도의 검토 단계로 정하는 방법을 생각할 수 있습니다. 예를 들어 동아리 행사 신청 페이지를 하루 만에 만들었다면 화면 완성과 운영 준비를 각각 확인합니다. 신청자가 두 번 누를 때 기록이 중복되는지, 담당자가 바뀌어도 신청 내역을 관리할 수 있는지 직접 살펴보는 방식입니다. 이 예시는 원문에 나온 사례가 아니라 원칙을 구체화한 편집상의 제안입니다. 팀은 생성한 코드의 양보다 실제 사용자가 겪을 실패를 얼마나 설명하고 처리할 수 있는지로 완성도를 판단할 수 있습니다. 그런 기준을 먼저 합의하면 빠른 실험의 이익을 유지하면서도 인수인계 비용을 더 정확하게 예상할 수 있습니다.
