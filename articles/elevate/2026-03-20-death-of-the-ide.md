# [Is the IDE dead?](https://addyo.substack.com/p/death-of-the-ide)

2026.03.20 · Addy Osmani · Elevate

통합 개발 환경인 IDE가 사라지는지 묻는 제목에 대해, Addy Osmani는 개발 업무의 중심이 이동하고 있다고 답합니다. 파일을 열어 직접 수정하는 반복에서 의도를 정하고 에이전트에 작업을 맡긴 뒤 결과를 검토하는 반복으로 옮겨간다는 설명입니다. Conductor, GitHub Copilot Agent, Jules 등의 사례를 통해 계획, 진행 상태, 변경 비교와 검토를 보여주는 화면이 중요해졌다고 말합니다. 개발자가 관리하는 기본 단위도 파일에서 수행 중인 작업으로 넓어집니다.

이 변화에는 여러 작업을 충돌 없이 분리하는 공간, 백그라운드 실행, 사람의 개입이 필요한 시점을 알리는 기능이 필요합니다. 저자는 Git 작업 트리처럼 에이전트별 수정 영역을 나누는 방식과, 작업 상태를 중심으로 구성한 인터페이스를 소개합니다. 그러나 정확한 코드 탐색과 대화형 디버깅, 복잡한 시스템의 이해에는 기존 IDE의 장점이 남습니다. 거의 맞지만 미묘하게 틀린 변경을 조사할 때 사람이 직접 코드를 다루는 경로가 여전히 중요하다는 설명입니다.

병렬 에이전트가 많아지면 작성 부담 대신 검토 피로와 통제 비용이 커질 수 있습니다. 어떤 도구와 저장소에 접근했는지, 어떤 권한을 가졌는지, 어느 변경부터 확인해야 하는지가 새로운 과제가 됩니다. 저자는 이를 편집기를 없애는 변화보다 개발 환경의 기능이 바깥으로 확장되는 변화로 봅니다. 작업을 지휘하는 화면과 깊이 조사하는 편집기가 함께 남을 수 있다는 전망입니다. 이는 당시 도구들에서 읽은 방향이며 개발자의 모든 작업이 이미 전환되었다는 선언은 아닙니다.

편집자의 관점에서는 새 도구를 평가할 때 동시에 실행할 수 있는 에이전트 수만 보면 부족합니다. 하나가 막혔을 때 이유를 알 수 있는지, 작업을 중단하거나 넘겨받을 수 있는지, 검토한 변경과 실제 반영한 변경이 같은지 확인할 수 있어야 합니다. 이런 항목은 원문의 제품 비교 점수가 아니라 도입 판단에 활용할 질문입니다. 에이전트마다 별도의 공간이 있어도 공통 인터페이스를 서로 다르게 바꾸면 통합 단계에서 충돌할 수 있습니다. 따라서 작업 경계와 합칠 순서를 함께 설계해야 합니다. 좋은 개발 환경은 손으로 입력하는 시간을 줄이면서도 사람이 필요한 순간에 충분한 정보를 얻도록 돕는 환경입니다. 운영과 검토의 부담까지 포함해야 실제 작업 방식이 나아졌는지 판단할 수 있습니다.
