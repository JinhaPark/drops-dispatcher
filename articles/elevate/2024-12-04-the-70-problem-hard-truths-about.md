# [The 70% problem: Hard truths about AI-assisted coding](https://addyo.substack.com/p/the-70-problem-hard-truths-about)

2024.12.04 · Addy Osmani · Elevate

AI로 코드를 빨리 만들 수 있는데도 소프트웨어의 품질이 그만큼 좋아지지 않는 이유를 Addy Osmani는 개발 현장에서 찾습니다. 초기 시제품을 만드는 사람은 눈에 보이는 결과를 빠르게 얻지만, 실제 운영에 필요한 예외 처리와 유지보수에서 어려움을 만납니다. 경험 많은 개발자는 생성된 코드를 검토하면서 구조와 안전성을 보완합니다. 반면 기본 지식이 부족하면 그럴듯한 결과를 판단하기 어렵습니다. 제목의 수치는 보편적으로 측정한 완성률이 아니라 시제품과 신뢰할 수 있는 제품 사이의 간극을 표현하는 장치입니다.

저자는 빠른 생성 뒤에 남는 일을 강조합니다. 오류 하나를 고치려다 다른 문제가 생길 수 있고, 코드가 작동해도 사용 조건이나 보안을 놓칠 수 있습니다. 제안하는 작업 방식은 범위를 작게 나누고 결과를 검토하며 테스트와 설계 이유를 남기는 것입니다. 에이전트가 실행과 검증을 더 많이 맡더라도 요구사항을 명확히 설명하고 품질을 판단하는 능력이 필요합니다. 접근성, 느린 환경에서의 성능, 실제 사용자의 어려움을 살피는 일도 중요합니다. 글은 개발 속도와 제품의 유용성을 같은 성과로 취급하지 말라고 주장합니다.

이 관점을 프로젝트 평가에 적용한다면 생성한 코드의 양보다 남아 있는 불확실성을 살피는 편이 유용합니다. 화면이 열리는지 확인하는 단계와 데이터가 손상되지 않는지 확인하는 단계는 서로 다른 위험을 다룹니다. 따라서 시제품의 완료 기준과 배포 가능한 제품의 완료 기준을 따로 적어 두면 기대를 조정하기 쉽습니다. 팀은 기능마다 실패할 수 있는 조건을 정하고, AI가 만든 설명과 실제 동작이 일치하는지 확인할 수 있습니다. 검토할 수 없는 크기의 변경은 속도보다 확인 비용을 먼저 늘릴 수 있습니다.

학습 측면에서도 결과를 얻는 과정과 원리를 이해하는 과정을 함께 설계해야 합니다. 생성된 구현을 자신의 말로 설명하고, 조건을 바꾸었을 때 어떤 부분이 깨질지 예상해 보는 활동이 판단력을 점검하는 방법이 됩니다. 이는 모든 코드를 손으로 작성해야 한다는 뜻은 아닙니다. 자동화한 작업의 결과를 책임질 만큼 이해하고 있는지가 기준입니다. 이 글은 특정 도구의 성능 순위보다 개발자의 역할이 어디에 남는지를 묻습니다. 품질의 기준을 먼저 정한 뒤 AI로 반복 작업을 줄여야 속도 향상이 제품의 개선으로 이어집니다.
