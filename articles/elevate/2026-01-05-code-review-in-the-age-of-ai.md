# [Code Review in the Age of AI](https://addyo.substack.com/p/code-review-in-the-age-of-ai)

2026.01.05 · Addy Osmani · Elevate

AI가 코드를 빨리 작성할수록 변경이 제대로 작동한다는 근거를 마련하는 일이 중요해집니다. Addy Osmani는 코드 검토의 병목이 타이핑 속도에서 검증 능력으로 이동했다고 설명합니다. 작성자가 테스트 결과나 실제 실행 증거를 남기지 않으면 검토자가 그 일을 대신 해야 합니다. 글은 혼자 개발하는 경우와 여러 사람이 유지보수하는 팀을 구분하면서도, 어느 쪽이든 결과를 확인하고 책임지는 사람이 필요하다는 원칙을 제시합니다.

개인 개발자는 자동 테스트와 빠른 수정 반복을 활용할 수 있지만, 최종 기능을 직접 실행하고 위험한 변경을 자세히 살펴야 합니다. 팀에서는 검토가 지식을 공유하고 이후 장애에 대응할 담당자를 준비시키는 과정이기도 합니다. 저자는 큰 AI 생성 변경을 작은 커밋과 검토 요청으로 나누고, 보안과 업무 맥락처럼 자동 검사가 놓칠 부분에 사람의 시간을 쓰라고 권합니다. 검토 도구의 불필요한 댓글을 줄이는 설정도 중요하다고 설명합니다.

구체적인 제안은 변경 요청에 네 가지 정보를 담는 것입니다. 무엇을 왜 바꿨는지, 어떻게 동작을 확인했는지, 위험 수준과 AI가 맡은 부분은 무엇인지, 검토자가 어디에 집중해야 하는지를 밝힙니다. 인증이나 결제처럼 영향이 큰 영역에는 별도의 보안 검토를 요구합니다. AI의 검토 의견은 추가 확인을 돕는 자료로 취급합니다. 저자는 여러 조사 수치를 인용하지만, 핵심은 특정 비율을 목표로 삼는 것보다 작성자가 변경의 근거를 설명할 수 있어야 한다는 주장입니다.

편집자의 관점에서는 검증 자료의 존재와 검증의 적절성을 구별해야 합니다. 테스트가 통과했다는 문장만으로는 새 요구사항이 실제로 시험되었는지 알 수 없습니다. 예를 들어 환불 로직을 바꿨다면 정상 처리뿐 아니라 중복 요청이나 외부 서비스 실패를 어떻게 다뤘는지 확인할 수 있어야 합니다. 이는 원문 사례의 재현이 아니라 검토 원칙을 구체화한 예시입니다. 팀은 모든 변경에 같은 분량의 문서를 요구하기보다 영향에 맞는 증거를 정할 수 있습니다. 작은 문구 수정과 계정 권한 변경의 확인 절차가 같을 이유는 없습니다. 검토 요청이 늘어날 때에는 작성 속도뿐 아니라 대기 시간과 재검토 횟수도 살펴야 실제로 배포가 빨라졌는지 판단할 수 있습니다.
