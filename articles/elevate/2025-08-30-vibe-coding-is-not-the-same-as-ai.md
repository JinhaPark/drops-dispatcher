# [Vibe coding is not the same as AI-Assisted engineering.](https://addyo.substack.com/p/vibe-coding-is-not-the-same-as-ai)

2025.08.30 · Addy Osmani · Elevate

Addy Osmani는 바이브 코딩과 AI를 활용한 소프트웨어 엔지니어링을 구분해야 한다고 주장합니다. 전자는 코드의 세부 사항을 깊이 확인하지 않은 채 대화로 빠르게 결과를 만드는 탐색 방식입니다. 후자는 설계와 테스트, 검토 절차 안에서 AI를 사용하는 접근입니다. 두 방식을 같은 이름으로 부르면 실제 운영에 필요한 책임과 기술이 가려질 수 있습니다. 저자는 AI가 초안을 만드는 속도와 사람이 제품의 정확성과 유지보수를 책임지는 일을 별개의 문제로 봅니다.

바이브 코딩은 일회성 도구나 시제품을 만들고 아이디어를 시험할 때 유용할 수 있습니다. 그러나 눈앞에서 작동한다는 사실만으로 실제 부하와 보안 요구를 충족한다고 볼 수는 없습니다. 구조를 이해하는 사람이 없으면 요구사항이 바뀌었을 때 수정도 어려워집니다. 글은 검토하지 않은 큰 변경을 동료에게 넘기는 행위가 부담을 이전한다고 지적합니다. 반대로 지나친 절차로 모든 실험을 막는 태도 역시 바람직한 해법으로 제시하지 않습니다.

대안은 필요한 자유와 검증 기준을 함께 정하는 것입니다. 명세에 요구사항과 완료 조건을 적고, AI가 만든 변경을 사람이 이해하며, 테스트와 검토로 확인합니다. 저자는 이를 AI의 도움을 거절하는 방식이 아니라 엔지니어링의 기존 책임을 유지하는 방식으로 설명합니다. 여러 실패 사례는 문제를 보여 주는 예시이지만, 모든 AI 사용이 같은 결과를 낸다는 뜻은 아닙니다. 적용 목적과 실패의 영향을 구분하는 판단이 중요합니다.

실무에서는 시제품을 운영 제품으로 바꾸는 경계를 명시하는 방법을 생각할 수 있습니다. 가령 내부 행사 신청 화면을 실험할 때는 가짜 자료로 흐름을 확인해도 충분하지만, 실제 참석자의 개인정보를 저장하기 시작하면 접근 권한과 삭제 방식까지 검토해야 합니다. 화면이 같더라도 책임의 범위가 달라지는 것입니다. 이때 처음 만든 코드를 얼마나 많이 재사용했는지는 핵심 기준이 아닙니다. 현재의 요구를 누가 이해하고 있으며, 문제가 생겼을 때 무엇을 확인하고 되돌릴 수 있는지가 더 직접적인 질문입니다. 팀은 실험의 결과와 운영 승인을 구분해 기록함으로써 빠른 탐색의 장점을 유지하면서도 시제품의 우연한 성공을 검증의 완료로 오해하는 일을 줄일 수 있습니다.
