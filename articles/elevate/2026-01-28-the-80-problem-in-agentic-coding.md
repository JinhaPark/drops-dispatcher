# [The 80% Problem in Agentic Coding](https://addyo.substack.com/p/the-80-problem-in-agentic-coding)

2026.01.28 · Addy Osmani · Elevate

AI가 코드의 상당 부분을 작성하게 되었어도 소프트웨어를 이해하고 책임지는 문제는 남습니다. Addy Osmani는 일부 개발자의 경험을 소개하면서, 과거의 마지막 구현 구간보다 잘못된 전제와 이해 부족이 더 중요한 제약이 되고 있다고 주장합니다. 에이전트가 초기에 요구를 오해한 채 기능을 확장하거나, 지나친 추상화와 사용하지 않는 코드를 쌓는 사례를 설명합니다. 제목의 80%는 모든 팀에 적용되는 성능 보증이 아니라 변화의 방향을 논의하기 위한 출발점입니다.

글의 중심 개념은 이해 부채입니다. 코드가 실행되고 테스트가 통과하더라도 담당자가 구조와 이유를 설명하지 못하는 상태가 누적될 수 있다는 뜻입니다. 생성량이 늘어도 사람의 검토와 조직의 조정이 따라가지 못하면 전체 처리 속도는 높아지지 않습니다. 저자는 새 개인 프로젝트와 오래된 조직의 코드베이스를 구분합니다. 기존 시스템에는 문서로 남지 않은 제약과 여러 팀의 의존성이 있으므로, 빠른 시제품 제작 경험을 그대로 옮기기 어렵다는 설명입니다.

대안으로는 구현 절차를 매번 지시하기보다 성공 조건과 테스트를 먼저 정하고 에이전트가 반복하도록 하는 방식을 제안합니다. 새로운 맥락에서의 추가 코드 검토, 자동 검사, 제한된 작업 범위, 중요한 설계 결정에 대한 사람의 판단을 함께 둡니다. 생성된 코드를 설명하게 하고 직접 구현하는 연습도 유지하라고 권합니다. 이때 성공 조건 자체가 잘못되면 반복 실행이 오류를 확대할 수 있습니다. 저자는 생산성에 관한 과장과 학습 능력 약화의 우려도 인정합니다.

편집자의 관점에서 이해 부채를 살피려면 코드 작성 비율과 다른 질문이 필요합니다. 변경의 담당자가 실패할 수 있는 조건을 설명할 수 있는지, 다른 동료가 운영 중 문제를 추적할 수 있는지, 다음 수정의 영향을 예상할 수 있는지 확인하는 방식입니다. 이런 질문은 원문이 제시한 표준 지표가 아니라 팀에서 논의할 수 있는 예시입니다. AI 없이 모든 줄을 다시 작성하게 할 필요는 없지만, 결과를 승인할 근거는 남아야 합니다. 특히 작성한 테스트가 구현의 가정을 그대로 복제했다면 통과 여부만으로 요구 충족을 판단하기 어렵습니다. 외부에서 관찰할 동작을 기준으로 검증하고, 설명하지 못하는 부분을 학습 과제로 남기면 생성 속도와 이해의 간격을 더 구체적으로 다룰 수 있습니다.
