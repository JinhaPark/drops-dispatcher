# [MCP: What It Is and Why It Matters](https://addyo.substack.com/p/mcp-what-it-is-and-why-it-matters)

2025.03.27 · Addy Osmani · Elevate

애디 오스마니는 AI가 외부 도구와 데이터를 이용하려면 연결 방식의 파편화를 해결해야 한다고 설명합니다. 모델과 서비스의 조합마다 별도 코드를 만들면 연결 수가 늘수록 관리 부담도 커집니다. MCP는 이를 공통 규약으로 줄이려는 접근입니다. AI를 사용하는 애플리케이션 쪽의 클라이언트와 기능을 제공하는 서버가 연결되고, 서버는 사용할 수 있는 기능과 입력 형식을 알립니다. 모델의 지능 자체를 바꾸는 기술이라기보다 도구를 발견하고 호출하는 접점을 정리하는 기술이라는 점이 핵심입니다.

글은 Blender, Figma, 브라우저, GitHub 등과 연결한 사례를 통해 창작과 개발 작업을 여러 도구에 걸쳐 이어가는 가능성을 소개합니다. 서버를 만드는 개발자는 실제 애플리케이션의 기능을 호출하고 결과와 오류를 돌려주는 부분을 구현해야 합니다. 공통 규약이 있다고 모델의 판단이나 작업 성공이 보장되지는 않습니다. 저자는 권한, 실행 지연, 도구 오용, 여러 단계 중 일부만 성공하는 상황을 과제로 다룹니다. 당시 생태계의 전망과 시연은 실제 운영 환경에서의 보증과 구분해서 읽어야 합니다.

이를 업무 흐름으로 생각하면, 고객 요청을 읽고 처리 기록을 만든 다음 담당자에게 알리는 작업을 예로 들 수 있습니다. 세 도구의 호출 형식이 통일되어도 첫 기록을 만든 뒤 알림이 실패하면 전체 작업은 끝나지 않습니다. 이때 모든 단계를 처음부터 반복하면 같은 기록이 중복될 수 있습니다. 따라서 연결 규약과 별도로 어느 단계까지 완료했는지 확인하고 이어갈 방법이 필요합니다. 도구가 많아질수록 연결의 편리함과 완료 상태를 판단하는 어려움이 동시에 커질 수 있다는 뜻입니다.

실무적인 출발점은 기능을 많이 연결하는 것보다 한 작업의 성공 조건을 분명하게 만드는 데 있습니다. 읽기만 필요한 단계와 데이터를 바꾸는 단계를 구분하고, 반환된 결과가 실제 변경을 입증하는지도 확인할 수 있어야 합니다. 예를 들어 요청을 접수했다는 응답과 처리를 끝냈다는 응답은 의미가 다릅니다. 이런 차이를 도구 설명과 결과에 담으면 사람과 AI 모두 다음 행동을 판단하기 쉬워집니다. MCP의 가치는 연결을 공통화하는 데 있으며, 그 위에서 신뢰할 수 있는 업무를 만드는 일은 서비스 설계와 운영 판단으로 이어집니다.
