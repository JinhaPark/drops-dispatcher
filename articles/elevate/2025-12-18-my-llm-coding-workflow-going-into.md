# [My LLM coding workflow going into 2026](https://addyo.substack.com/p/my-llm-coding-workflow-going-into)

2025.12.18 · Addy Osmani · Elevate

Addy Osmani는 2026년을 앞두고 자신의 AI 코딩 방식을 정리하며, 좋은 결과를 만드는 핵심으로 개발자의 판단과 체계적인 작업 절차를 꼽습니다. 먼저 사용자 요구, 예외 상황, 구조와 테스트 전략을 명세로 정리하고, 이를 작은 구현 단계로 나눕니다. AI가 초안을 만들더라도 사람이 내용을 검토한 뒤 코딩을 시작합니다. 각 단계는 결과를 이해하고 시험할 수 있는 크기로 유지하며, 한 번에 큰 기능을 생성하다 생기는 중복과 불일치를 줄이려는 접근입니다.

다음 조건은 필요한 맥락을 정확하게 제공하는 일입니다. 관련 코드, 현재 버전의 문서, 반드시 유지할 동작과 피해야 할 방법을 전달합니다. 프로젝트의 규칙과 좋은 구현 예시를 파일이나 재사용 가능한 스킬로 남기는 방법도 소개합니다. 저자는 상황에 따라 모델을 바꾸거나 다른 모델에 검토를 맡기지만, 도구의 답변을 그대로 신뢰하지는 않습니다. 브라우저 실행 결과와 오류 기록처럼 실제 환경에서 얻은 정보도 수정 과정에 포함합니다.

구현 뒤에는 테스트와 코드 검토를 수행하고, 작은 변경을 자주 커밋해 되돌릴 지점을 만듭니다. 병렬 작업에는 분리된 작업 공간을 활용하되, 여러 에이전트를 동시에 감독하는 인지적 부담을 인정합니다. 지속적 통합 환경의 검사 결과를 다시 AI에 전달하면 생성과 수정의 반복을 돕는다는 설명입니다. 저자는 자신이 설명할 수 있는 코드만 반영한다는 원칙을 강조하며, AI를 통해 배우는 시간과 직접 구현하는 연습도 남겨두라고 권합니다.

편집자의 관점에서 이 작업 방식의 가치는 특정 제품을 모두 도입하는 데 있지 않습니다. 기존 팀의 개발 과정에서 무엇을 확인하지 못하고 있는지 찾는 출발점으로 읽을 수 있습니다. 예를 들어 테스트 실행은 자동화되어 있어도 실패 원인을 사람이 재구성해야 한다면, 다음 개선 과제는 새 모델 선택보다 실행 기록의 정리일 수 있습니다. 반대로 검증할 동작이 명확하지 않다면 자동 반복 횟수를 늘려도 완료 여부를 판단하기 어렵습니다. 이런 적용 예시는 저자의 경험을 토대로 확장한 해석이며 보장된 생산성 수치를 뜻하지 않습니다. 팀은 작은 과제 하나에서 검토 시간과 수정 횟수를 함께 관찰하며, 자신의 코드베이스에 맞는 절차를 선택할 수 있습니다.
