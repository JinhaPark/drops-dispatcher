# [Why I use Cline for AI Engineering](https://addyo.substack.com/p/why-i-use-cline-for-ai-engineering)

2025.01.30 · Addy Osmani · Elevate

Addy Osmani는 Cline을 코드 제안 기능을 넘어 개발 환경과 상호작용하는 도구로 평가합니다. 편집기 안에서 파일을 읽고 수정하는 작업에 터미널 실행과 브라우저 확인을 연결하면 작성한 코드의 실제 동작을 살필 수 있다는 설명입니다. 이 글은 최초 발행 뒤 갱신된 내용도 포함하며, 저자의 사용 경험을 바탕으로 작성되었습니다. 따라서 경쟁 도구의 당시 기능과 가격을 현재의 비교 기준으로 그대로 받아들일 수는 없습니다. 핵심 논점은 복잡한 개발 작업에서 자동화의 범위와 사람의 통제를 어떻게 함께 확보하는가에 있습니다.

저자가 강조하는 기능은 필요한 자료를 선택해 제공하는 문맥 관리, 작업에 맞춘 모델 선택, 계획과 실행을 구분하는 방식입니다. 변경을 되돌릴 수 있는 체크포인트와 실행 전 승인은 실험 과정의 통제 수단으로 소개합니다. 외부 도구를 연결하는 MCP를 활용하면 조직의 기존 작업 흐름과도 결합할 수 있습니다. 반면 설정과 사용량 관리의 부담이 생깁니다. 확장 프로그램을 무료로 설치하는 것과 모델 사용 비용이 없는 것은 다릅니다. 저자가 제시한 비용 절감 경험도 모든 작업에서 재현되는 수치로 이해해서는 안 됩니다.

이 접근을 팀에 적용한다면 자동화할 행동의 범위를 먼저 정하는 것이 유용합니다. 파일 수정, 명령 실행, 외부 서비스 접근은 서로 다른 영향을 만들기 때문입니다. 예를 들어 시험용 환경에서 화면을 확인하는 작업과 실제 사용자 데이터에 접근하는 작업에 같은 승인 기준을 적용하기는 어렵습니다. 어떤 정보가 모델로 전달되는지, 실행 결과를 어디에 남기는지, 실패했을 때 무엇을 되돌릴 수 있는지 확인해야 합니다. 이는 도구의 편의성을 평가하는 일과 함께 검토할 운영 조건입니다.

또한 계획을 보여 주는 기능만으로 계획의 타당성이 보장되지는 않습니다. 개발자는 변경 이유와 성공 조건을 검토하고, 실행 뒤에는 결과가 그 조건을 충족하는지 확인해야 합니다. 복구 기능도 모든 외부 효과를 취소한다고 가정해서는 안 되므로 실제 복구 범위를 시험할 필요가 있습니다. 이 글의 의미는 도구가 일을 많이 수행할수록 판단이 불필요해진다는 데 있지 않습니다. 반복적인 조작을 맡기면서도 중요한 선택과 결과를 확인할 수 있는 작업 흐름을 설계하자는 데 있습니다. 팀의 요구와 관리 역량에 맞는 도입 범위를 정해야 합니다.
