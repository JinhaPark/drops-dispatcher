# [The Agent Stack Bet](https://addyo.substack.com/p/the-agent-stack-bet)

2026.04.18 · Addy Osmani · Elevate

Addy Osmani는 운영 환경의 AI 에이전트를 어렵게 만드는 문제가 모델의 능력만은 아니라고 주장합니다. 공용 계정, 끊기기 쉬운 실행 상태, 흩어진 업무 정보와 자체 제작한 연결 코드가 신뢰성과 관리의 한계를 만든다는 설명입니다. 에이전트가 작업을 완료했다고 보고해도 실제 데이터나 권한 처리에는 문제가 남을 수 있습니다. 저자는 앞으로 필요한 기반을 에이전트의 고유한 신원, 통합된 맥락, 지속 가능한 실행, 공통 플랫폼의 네 영역으로 정리합니다.

고유한 신원은 어떤 에이전트가 무엇을 했는지 추적하고 권한을 회수할 수 있게 하는 조건입니다. 저자는 사람의 인증 정보를 빌려 쓰게 하기보다 플랫폼과 네트워크에서 정책을 강제해야 한다고 말합니다. 업무 맥락도 열린 브라우저나 첨부한 파일에 한정하지 않고 여러 업무 시스템에 연결해야 한다고 제안합니다. 다만 이런 광범위한 연결이 정당한 접근 범위를 자동으로 보장한다는 뜻은 아닙니다. 신원과 정책이 함께 작동해야 한다는 논지입니다.

긴 업무에는 세션이 유지되는 수준을 넘어 재시작, 담당자 교체, 인증 정보 변경 후에도 이어지는 상태 관리가 필요합니다. 진행 상황의 저장과 인계, 오래 유지되는 기록, 필요한 순간 사람에게 승인을 요청하는 절차를 포함합니다. 마지막으로 저자는 메모리, 관찰 도구, 재시도와 실행 조정을 팀마다 다시 만들지 않도록 공통 기반을 활용하자고 권합니다. 공개된 구성 요소로 시작해 운영 플랫폼으로 확장하면서, 팀의 역량을 고유한 업무 판단과 제품 기능에 쓰자는 제안입니다.

편집자의 해석으로는 이 글을 플랫폼 구매를 권하는 단일 결론보다 기반의 요구사항을 점검하는 틀로 읽을 수 있습니다. 예를 들어 여러 날 걸리는 업무라면 실패한 지점에서 재개할 때 이미 수행한 외부 작업을 다시 실행하지 않는지 확인해야 합니다. 신원을 구별하더라도 실제 권한이 모두 같다면 통제의 이점이 제한될 수 있습니다. 이런 질문은 원문에서 검증한 제품 성능이 아니라 제안을 적용하며 살펴볼 조건입니다. 공통 플랫폼을 선택해도 데이터 경계와 장애 대응의 책임까지 사라지지는 않습니다. 팀은 제공되는 기능의 이름보다 중단, 인계, 권한 회수 상황에서 실제로 남는 기록과 동작을 시험해야 합니다. 그래야 자체 개발을 줄이면서도 장기간 맡긴 업무의 결과를 설명할 수 있습니다.
