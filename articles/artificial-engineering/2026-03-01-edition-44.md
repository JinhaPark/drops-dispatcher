# [From Solo Agent to Parallel Fleet](https://www.linkedin.com/pulse/from-solo-agent-parallel-fleet-andr%C3%A9-lindenberg-ncspf)

2026-03-01 · André Lindenberg · Edition 44

이번 호는 Claude Code의 병렬 작업 기능을 중심으로 개발자의 역할이 어떻게 달라지는지 살펴봅니다. 저자가 소개하는 /simplify는 재사용, 품질, 효율을 서로 다른 관점에서 검토하게 하고, /batch는 큰 작업을 나누어 독립된 작업 공간에서 수행하도록 구성합니다. 개별 작업은 테스트와 검토 가능한 변경 결과로 이어집니다. 개발자는 한 에이전트에게 차례로 지시하는 사람에서, 작업 경계를 정하고 결과를 통합하는 사람으로 이동합니다.

저자는 이런 방식의 효과가 저장소 구조에 달려 있다고 봅니다. 서로 분리하기 쉬운 모듈과 명확한 프로젝트 규칙이 있을수록 병렬화가 유리합니다. 별도의 Git 작업 공간은 파일 충돌을 줄이지만, 결과의 의미까지 자동으로 일치시키지는 않습니다. 따라서 원문의 낙관적인 생산성 전망은 독립적으로 나눌 수 있는 작업이라는 조건과 함께 읽어야 합니다. 여러 에이전트를 실행했다는 사실만으로 전체 변경의 정확성을 보장할 수는 없습니다.

실제로는 병렬 작업을 시작하기 전에 공통 부분과 개별 부분을 구분하는 것이 도움이 됩니다. 여러 화면의 문구 수정은 각각 맡길 수 있지만, 화면들이 사용하는 공통 데이터 형식의 변경은 먼저 합의해야 합니다. 각 담당자가 자기 폴더의 테스트를 통과해도, 결과를 합치면 다른 화면이 깨질 수 있기 때문입니다. 그러므로 작업 지시에는 수정할 범위뿐 아니라 의존하는 계약과 완료 조건도 포함하는 편이 좋습니다. 이 예시는 원문의 분해와 검토라는 주제를 실제 협업 절차로 해석한 것입니다.

검토 비용 또한 병렬화의 계산에 넣어야 합니다. 변경 요청이 한꺼번에 많이 생기면 코드 작성은 빨라져도 사람이 읽고 판단하는 시간이 병목이 될 수 있습니다. 작은 단위로 결과를 모으고, 공통 규칙에 어긋난 변경을 먼저 걸러내면 검토자가 중요한 차이에 집중하기 쉽습니다. 동시에 각 결과의 출발 버전과 테스트 범위를 기록해야 나중에 충돌 원인을 추적할 수 있습니다. 병렬 에이전트의 장점은 수를 늘리는 데서 바로 나오기보다, 나눌 수 있는 일을 정확히 골라 독립성을 유지하고 마지막 통합 검증을 책임지는 운영 방식에서 나옵니다.
