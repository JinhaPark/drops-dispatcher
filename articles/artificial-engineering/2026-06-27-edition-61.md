# [From Prompts to Loops: The Next Step of Agent Engineering](https://www.linkedin.com/pulse/from-prompts-loops-next-step-agent-engineering-andr%C3%A9-lindenberg-wnqre)

2026-06-27 · André Lindenberg · Edition 61

코딩 에이전트에게 매번 다음 일을 지시하는 대신, 일을 발견하고 검증하며 상태를 남기는 시스템을 만든다면 개발자의 역할은 달라집니다. 이번 호에서 저자는 이를 루프 엔지니어링이라고 설명합니다. 중심은 더 좋은 문장을 쓰는 기술이 아니라 반복되는 문제를 지속적으로 처리하는 구조입니다. 따라서 이미 열어 둔 편집기에 지시를 추가하는 데서 출발하기보다 어떤 업무를 맡기고 무엇을 완료로 인정할지 먼저 정해야 합니다. 에이전트는 그 구조 안에서 판단과 구현을 담당하는 구성 요소입니다.

저자는 실행 계기, 격리된 작업 공간, 지속적으로 읽을 지침, 실제 행동하는 도구, 별도의 검증자, 실행 상태를 주요 요소로 제시합니다. 실패한 테스트나 새 이슈처럼 작업 단위를 스스로 발견하고, 수정한 결과를 독립적인 검사에 통과시킨 뒤 다음 행동을 결정하는 방식입니다. 특히 완료라는 모델의 선언과 완료를 입증하는 검사는 다릅니다. 구현자와 검증자를 분리해도 검사 기준 자체가 목표를 잘못 대변하면 시스템은 잘못된 결과를 반복해서 생산할 수 있습니다.

따라서 이 글에서 가장 어려운 설계 문제는 에이전트를 오래 실행하는 기술보다 무엇을 검증할지 정하는 일입니다. 저자는 같은 구조도 사용자의 이해 수준에 따라 다른 결과를 낸다고 강조합니다. 업무를 잘 아는 사람이 속도를 높이는 데 사용할 수도 있고, 이해를 포기한 채 결과만 받아들이는 데 사용할 수도 있기 때문입니다. 반복 횟수와 비용의 상한, 사람에게 돌려줄 조건도 필수 요소로 다룹니다. 이런 설명은 자율 실행 자체를 성과로 삼지 말라는 운영상의 주장입니다.

실무적으로는 반복할수록 손해가 누적되는 실패를 먼저 상상할 필요가 있습니다. 잘못된 기준으로 의존성을 갱신하거나 의미 없는 테스트를 추가하면 매번 성공 표시가 나와도 유지보수 부담은 커집니다. 따라서 초기에 작은 표본을 사람이 읽고, 통과한 결과가 실제 목적을 달성했는지 확인해야 합니다. 입력 범위가 바뀌었을 때 기존 검사도 유효한지 다시 평가할 필요가 있습니다. 자동화가 맡는 반복과 사람이 맡는 기준의 책임을 분명히 할 때 이 구조의 장점이 살아납니다. 실행을 맡기는 일과 판단의 책임을 버리는 일은 구분해야 합니다.
