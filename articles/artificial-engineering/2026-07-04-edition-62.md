# [Plan the Loop Before You Build It](https://www.linkedin.com/pulse/plan-loop-before-you-build-andr%C3%A9-lindenberg-y0t1e)

2026-07-04 · André Lindenberg · Edition 62

반복되는 업무라고 해서 모두 에이전트 루프로 만들 가치가 있는 것은 아닙니다. 이번 호에서 저자는 구현에 들어가기 전에 문제와 목표를 함께 검토하는 Loop Engineering Canvas를 소개합니다. 한 장의 틀에 필요한 결정을 적어 팀이 서로 다른 가정을 드러내도록 하는 도구입니다. 모델을 먼저 고르고 나중에 용도를 찾기보다, 어떤 일을 반복해서 처리해야 하고 어디까지 신뢰할 수 있어야 하는지 합의하자는 제안입니다. 이 문서는 시스템을 만들어 주지 않고 설계의 빈틈을 드러냅니다.

캔버스는 문제, 목표, 실행 계기, 행동, 상태, 한계, 통제, 모델과 프롬프트, 관찰 가능성의 아홉 요소를 다룹니다. 목표에는 다른 검사자가 실행할 수 있는 완료 조건을 적습니다. 모델 선택은 주변 조건이 정해진 다음의 문제로 둡니다. 실행 기록을 통해 어떤 입력에서 어떤 행동과 판단이 나왔는지 재구성하는 조건도 포함합니다. 저자는 단건을 사람이 처리할지, 단순한 스크립트를 만들지, 반복 비용을 감수하는 적응적 시스템을 만들지 비교해야 한다고 설명합니다.

사례들은 판단이 필요한 부분과 결정적으로 검사할 부분을 분리합니다. 의존성 변경에서는 빌드 도구가 결과를 확인하고, 테스트 생성에서는 주입한 결함을 실제로 발견하는지 검사합니다. 취약점 조사에는 발견을 반박하려는 별도 평가 절차를 둡니다. 저자의 핵심 주장은 모델이 모든 단계를 맡는 것보다 적절한 위치에서 제한적으로 판단하도록 구성하는 편이 낫다는 것입니다. 다만 각 사례의 성과 수치는 해당 환경의 결과이며 같은 캔버스를 작성한다고 재현되는 보장은 아닙니다.

실무에서는 완료 조건에 적힌 문장부터 의심해 볼 필요가 있습니다. 예를 들어 문의에 답변을 작성했다는 조건은 답변이 정책에 맞고 사용자의 문제를 해결했는지 확인하지 못합니다. 검사 기준을 더 엄격하게 만들면 비용과 예외 처리 부담도 함께 늘어납니다. 따라서 누락과 오판의 비용을 비교하고, 사람이 검토해야 하는 경계를 먼저 정하는 편이 타당합니다. 또한 실행 빈도와 재시도 횟수를 곱해 실제 운영 비용을 추산해야 합니다. 이 틀의 가치는 모든 칸을 채우는 데 있지 않고 자동화가 책임질 수 있는 범위를 팀이 설명할 수 있게 만드는 데 있습니다.
