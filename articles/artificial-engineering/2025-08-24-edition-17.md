# [From Prompt Engineering to AI-Driven Ecosystems: Building Bridges in AI](https://www.linkedin.com/pulse/from-prompt-engineering-ai-driven-ecosystems-building-lindenberg-iavre)

2025-08-24 · André Lindenberg · Edition 17

이번 호에서 저자는 AI의 발전을 더 영리한 답변을 만드는 문제에서 실제 업무 체계 안에 통합하는 문제로 옮겨 봅니다. 생성형 AI 시범 사업의 실패를 다루면서도 기술 자체가 무용하다는 결론을 서두르지 않습니다. 조직의 구조, 업무 절차, 사용자의 수용 방식이 성과를 가로막을 수 있다는 주장입니다. 이는 저자의 해석이며 모든 실패의 원인이 도입 방식이라는 뜻은 아닙니다. 어떤 업무를 개선하려는지와 무엇을 성공으로 측정할지를 먼저 정해야 기술의 한계와 조직의 문제를 구별할 수 있습니다.

오래된 Java 시스템을 현대화하는 사례는 이러한 관점을 구체화합니다. 기능이 오랫동안 쌓인 프로그램은 여러 구성 요소가 서로 의존하므로 코드를 옮기는 일만으로는 충분하지 않습니다. 저자는 재설계에 앞서 지식 그래프로 구성 요소와 의존 관계를 표현하자고 제안합니다. 어디가 강하게 연결되어 있고 어떤 부분을 비교적 독립적으로 바꿀 수 있는지 살피면 이행 순서를 정하는 데 도움이 됩니다. 그래프의 가치는 보기 좋은 그림보다 변경의 파급 범위를 드러내는 데 있습니다. 다만 조사에서 빠진 관계까지 자동으로 보장해 주지는 않습니다.

에이전트에 대한 평가는 더 신중합니다. 저자는 Salesforce의 도구 사용 평가를 근거로, 높은 기대와 실제 업무 수행 능력 사이에 상당한 차이가 있다고 설명합니다. 모델이 외부 도구와 데이터에 접근하도록 연결하는 MCP가 있어도 긴 문맥, 낯선 도구, 여러 영역이 얽힌 작업의 어려움까지 해결되지는 않는다는 것입니다. 평가 결과는 해당 과제와 조건에서 나온 관찰로 읽어야 합니다. Perplexity의 Comet은 브라우저 안에서 AI가 행동하는 방향을 보여 주지만, 새로운 인터페이스가 곧 안정적인 자율 실행을 입증하는 것은 아닙니다.

이런 불확실성 속에서 저자가 권하는 실용적인 출발점은 프롬프트의 일관성입니다. 역할과 목표, 결과 형식을 명시하고 지시를 구획하며, 사실 추출과 해석, 결론의 순서를 분명히 하자는 제안입니다. 쉬운 사례뿐 아니라 까다롭거나 모호한 사례도 예시로 제공하면 기대하는 동작을 더 구체적으로 전달할 수 있습니다. 이를 업무 설계로 확장하면 도입 목표, 기존 시스템의 관계, 실행 결과를 함께 확인하는 과정이 됩니다. 원문이 제시하는 방향은 분명하지만 각 도구가 모든 조직에서 같은 효과를 낸다는 보장은 없습니다. 실제 활용에서는 작은 범위의 작업부터 검증을 축적해야 합니다.
